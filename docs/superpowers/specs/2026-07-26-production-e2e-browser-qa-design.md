# 生产环境全方位 E2E 浏览器验收设计

## 背景

当前分支已经完成发卡用户后台升级，并创建 Pull Request `#1`。该功能合并并部署后，需要用最贴近真实生产的方式验证管理员后台和发卡用户后台，而不是只检查健康接口、SPA shell 或静态测试。

本验收设计采用用户确认的方案：部署后线上端到端验收，并允许临时启用或创建测试支付配置。验收过程可以创建临时发卡用户、订单、应用、规格、批次、卡密、设备和审计记录，并在测试结束后恢复配置、清理临时数据。

## 目标

- 验证管理员和发卡用户两种真实会话下的页面 UI、菜单路由和功能模块。
- 验证充值、审批、额度到账、发卡、核验、设备、流水、审计之间的数据关联。
- 验证发卡用户后台不是只实现功能，而是达到可用、清晰、低空白、不卡片拉伸的产品标准。
- 验证自建应用和管理员授权应用的规格/批次边界正确。
- 输出产品经理视角和资深开发工程师视角的修复建议。
- 不在日志、报告、记忆或提交中输出任何密码、token、服务器密码、完整卡密、真实支付敏感信息。

## 非目标

- 不做自动支付回调、退款、返佣、代理系统或新角色体系。
- 不做全量生产数据重置。
- 不修改真实商用支付配置的长期业务语义；测试配置必须可恢复。
- 不记录真实收款二维码地址、账号密码、token 或完整卡密。

## 前置条件

- Pull Request `#1` 已合并，并由 GitHub Actions 成功部署到生产。
- 生产 `/health` 返回健康状态。
- 可以使用管理员账号登录生产后台。
- 所有临时数据使用唯一前缀，例如 `E2E_UI_QA_YYYYMMDD_HHMMSS_`。
- 测试开始前读取并保存当前支付配置快照，测试结束后恢复。

## 测试数据策略

所有测试数据必须带固定前缀，并记录最小必要标识：

- 发卡用户：记录用户名前缀和用户 ID，不记录密码。
- 订单：记录订单号、状态、金额、到账额度，不记录上传凭证真实路径。
- 应用：记录 app_id、名称前缀、归属。
- 规格：记录 spec_id、规格名、类型、状态。
- 批次：记录 batch_no、数量、成本快照。
- 卡密：只记录数量、状态和脱敏样例，例如前后各 3 位，中间隐藏。
- 设备：记录设备数量、app 归属、发卡归属，不记录敏感指纹完整值。
- 审计和流水：记录动作、状态、资源类型、数量，不记录 token 或密码。

## 浏览器验收标准

每个页面至少检查桌面视口 `1440x900` 和宽屏视口 `1920x1080`。关键表单页和列表页额外检查移动视口 `390x844`。

页面通过标准：

- 页面主体非空，且显示与当前路由匹配的业务标题和关键内容。
- 无 JavaScript runtime exception。
- 无 `console.error`。
- 无未处理的 4xx/5xx 业务请求；认证边界预期的 401/403 不计为失败。
- 无错误 toast，如资源不存在、请求失败、白屏后的空提示。
- 首屏信息密度正常，不能出现大量空白造成页面像半成品。
- 卡片宽度不被横向拉长，充值金额和支付方式布局符合左右分区。
- 表格列宽、按钮、标签、弹窗不重叠、不挤压、不溢出容器。
- 侧边栏、顶部栏、角色标签和页面标题文案一致。
- 发卡用户后台不得显示可见文案“商户控制台”。

## 管理员后台覆盖

管理员菜单和模块：

- 运营总览：业务指标、趋势/列表、空态是否合理。
- 应用信息：应用列表、应用状态、跳转到接口/版本/规格是否正常。
- 公告管理和版本管理：空态、表格、操作按钮布局。
- 规格管理：规格字段完整，创建/编辑/删除敏感确认一致。
- 批次管理：批次列表、批次详情、卡密列表、统计信息。
- 卡密列表：搜索、状态、导出入口、脱敏显示。
- 设备管理：设备归属、发卡归属、应用归属、风险状态。
- 发卡用户管理：用户列表、额度、应用授权、删除清理边界。
- 充值配置：临时通道、固定金额、bonus 规则、二维码上传/删除控件。
- 充值订单：创建后的订单可查看、审批、拒绝、异常状态表达正确。
- 额度流水：充值入账、手动调整、发卡扣减记录可追溯。
- 财务运营：按审核时间统计，导出与页面数据一致。
- 操作审计：敏感动作成功/失败审计可查询。
- 运维中心：健康、备份、近期错误、证明文件清理干跑。
- 事件日志：SDK 核验/消费事件可查询。

## 发卡用户后台覆盖

发卡用户菜单和模块：

- 发卡工作台：额度、应用数、待办、通知、最近批次、最近订单布局合理。
- 充值发卡额度：金额在左、支付方式在右，金额卡片宽度收敛，凭证上传清晰。
- 我的订单：订单状态、取消边界、凭证信息、审核结果。
- 发卡额度流水：充值入账和发卡扣减按时间展示。
- 我的应用：新建应用使用弹窗，结果页不暴露敏感凭证；规格批次入口清晰。
- 批次管理：规格优先工作台，自建应用可管理规格，授权应用规格只读。
- 我的卡密：按应用、批次、状态、关键词搜索，导出结果数量正确。
- 设备记录：只看到自己自建应用或自己发出的授权应用卡密设备。
- 账号设置：页面不是误渲染首页，信息和更新入口布局正常。

## 端到端业务链路

### 充值链路

1. 管理员读取当前支付配置快照。
2. 管理员临时启用测试支付通道、固定金额和 custom bonus 规则。
3. 发卡用户读取充值配置。
4. 发卡用户提交固定金额充值订单并上传测试凭证。
5. 管理员查看订单和凭证。
6. 管理员审批订单。
7. 验证发卡用户额度增加，订单状态为已通过，额度流水新增入账。
8. 验证财务统计按审核时间计入，审计记录存在。
9. 验证重复审批被拒绝。

### 自建应用发卡链路

1. 发卡用户创建自建应用。
2. 发卡用户在自建应用创建规格。
3. 发卡用户预览发卡成本。
4. 发卡用户生成批次。
5. 验证额度扣减、批次成本快照、卡密数量和状态。
6. 验证重复批次号拒绝，不能免费增发。
7. 使用公开核验或 SDK 形态接口验证卡密。
8. 验证设备记录、事件日志和卡密状态更新。

### 管理员授权应用链路

1. 管理员创建测试应用和规格。
2. 管理员授权应用给发卡用户。
3. 发卡用户看到授权应用及其启用规格。
4. 发卡用户不能编辑/删除授权规格。
5. 发卡用户可以从授权规格生成批次。
6. 验证定价来源、成本快照、额度扣减和卡密列表。
7. 验证非授权应用或不可见规格被拒绝。

### 权限隔离链路

- 发卡用户访问管理员接口必须返回 403 或符合预期的拒绝。
- 未登录访问受保护接口必须返回 401。
- 发卡用户不能读取其他发卡用户的应用、批次、卡密、订单、设备。
- 应用使用用户不能登录发卡用户后台。

## 清理和恢复

清理顺序：

1. 取消或终结未完成的测试充值订单。
2. 删除测试发卡用户及其订单、证明文件、额度账户、流水。
3. 删除测试应用、规格、批次、卡密、设备和事件日志。
4. 恢复测试前支付配置快照。
5. 执行残留检查：发卡用户、订单、应用、批次、卡密、设备、流水、导出 CSV 中不得出现测试前缀。

如果清理失败：

- 立即停止继续创建新测试数据。
- 输出失败资源类型、脱敏 ID、失败接口状态和错误摘要。
- 不执行全表清理或生产重置。
- 由人工确认后再进行定向清理。

## 证据和报告

报告必须包括：

- GitHub Actions run 状态和部署 commit。
- `/health` 状态。
- 浏览器巡检结果：页面、视口、截图路径、console/error/network/toast 数量。
- 管理员链路结果：配置、订单、审批、财务、审计、设备。
- 发卡用户链路结果：充值、应用、规格、批次、卡密、设备、流水。
- 数据闭环统计：额度前后变化、订单数、批次数、卡密数、设备数、审计数。
- 清理恢复结果：支付配置是否恢复、测试前缀是否归零。
- 产品经理视角问题清单。
- 资深开发工程师视角问题清单。

报告不得包含：

- 管理员密码、发卡用户密码、token、cookie。
- 服务器密码、数据库密码、SSH 凭据。
- 完整卡密、完整设备指纹、真实支付账号或二维码敏感地址。

## 问题分级

- P0：权限泄露、扣费/入账错误、生产页面白屏、无法登录、无法充值、无法发卡、清理可能误删生产数据。
- P1：核心业务数据关联错误、重复提交造成数据异常、授权应用边界错误、测试数据无法清理。
- P2：页面大面积空白、卡片拉伸、表格挤压、弹窗错位、关键提示不清。
- P3：文案细节、列宽微调、提示语优化、非核心空态美化。

## 交付边界

本设计只定义验收和分析方案。执行验收前需要单独的实施计划，明确脚本、账号输入方式、数据前缀、截图目录、清理检查和失败停止条件。
